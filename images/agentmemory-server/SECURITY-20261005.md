## Zod limit investigation and targeted mitigation

User selected investigation of input limits. Actual 0.9.29 bundle tracing found
validateInput has no direct input callers: validateOutput delegates to it, and
its only callers validate CompressOutputSchema and SummaryOutputSchema in
generated provider output. The apparent import/input schemas are discarded
expressions in these bundles. Do not impose a memory-import size cap based on
those unused schema declarations.

patch-zod-output-limits.mjs patches both exact 0.9.29 bundle copies of the
shared validator. Before Zod runs, reject any generated facts/concepts/files/
keyDecisions/filesModified array above 1024 entries. These fixed schemas have
string elements, so this bounds their issue fan-out. Preserve existing
validation-result/error structure; no truncation or persistence of rejected
output. Compression retains its existing retry/failure path, and summarization
its existing validation-failure path. Ordinary memory save/search/import and
stored memories are unchanged. A legitimate generated output above the cap is
rejected; 1024 items per field is the explicit compatibility ceiling.

The patch asserts the upstream version and exact bundle shape. Its runnable
build regression checks valid output, the 1024 boundary, ordinary invalid
output/error shape, and rejection of all five oversized fields before invoking
Zod. Local tests pass against the actually installed Zod 4.6.5.

This is targeted mitigation, not a fixed Zod release: SDK protocol/client/server
validation also uses Zod, including schemas with continuable issues and async
paths. Globally overriding Zod error behavior or applying the unmerged
abortEarly proposal would be an incompatible/incomplete repair. That broader
CVE remains visible and unresolved.

### SQLite source alternatives and actual usage

Debian's CVE-2026-50812 tracker records a session-extension fix in `3.53.2-1`
and marks Trixie no-DSA. Newer Debian sources also address CVE-2026-50813.
However, changing the distribution/download source alone is not remediation:
CVE-2025-70873 concerns the zipfile extension, which Debian does not build,
and CVE-2021-45346 is disputed by SQLite developers and has no blanket fixed
release. A replacement must contain actual fixes and preserve required ABI.

This image needs no replacement shared SQLite library:

- Debian liblastlog2-2 depends on libsqlite3-0. The existing final-root purge
  already removes that login-bookkeeping consumer with the util-linux family.
  See https://packages.debian.org/trixie/liblastlog2-2.
- The actual v2 installed Depends/Pre-Depends graph has no surviving SQLite
  reverse dependency. All 549 retained ELF files were inspected; none has a
  libsqlite3 DT_NEEDED entry. The library itself was the 550th ELF file.
- The pinned entrypoint configures iii's state and KV modules as `file_based`.
  A `.db` suffix on `/data/state_store.db` is not evidence of SQLite storage.
- AgentMemory 0.9.29's only SQLite import is `mem::migrate`'s optional legacy
  importer, which dynamically imports `better-sqlite3`. That module is absent
  from the published package tree and its declared dependencies. The importer
  already returns an explicit missing-module error. SQLite purge does not
  remove a previously available migration capability.
- Installed JavaScript/SDK searches found no libsqlite3 dlopen path; the Claude
  SDK matches are SQLite MIME types. Native modules and the iii executable
  are included in the full ELF audit. Node's built-in SQLite is part of its
  binary, not this Debian shared library; removal is not a claim about any
  statically embedded SQLite implementation.

The follow-up reuses the existing removal auditor with an explicit `sqlite`
family. After the package-manager/util-linux purge, it rechecks the newly built
installed dependency closure and every retained ELF before `dpkg --purge
libsqlite3-0` (without force). It records original package-owned non-directory
files and then verifies both package absence and physical absence, including
the library symlink, implementation and copyright file. Builder SQLite remains
available until package work finishes; only the copied final root is stripped.

Local tests cover both removal families and reject injected Pre-Depends, ELF
imports and leftover package files. The auditor passes against the actual v2
root, inspecting 549 retained ELF files. Existing copied-root/native/SDK/offline
embedding checks and workflow service/state smoke tests remain enabled. CI and
Trivy must pass on the replacement candidate; Xray clearance still requires
rescanning that exact new image. The existing immutable v2 image is unchanged.
