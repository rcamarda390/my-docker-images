# CVE-2026-93355: downstream JWT email verification

Reviewed LiteLLM 1.94.3 (standalone), 1.101.3 (Headroom SDK), and current
upstream v1.105.1. The reviewed JWTHandler.get_user_email method accepts the
email without checking email_verified. JWTAuthManager.get_user_info passes
that email as the default identity and onward to get_user_object, whose fuzzy
lookup can select another user's email and schedule an sso_user_id update.
No usable official fixed release was established.

Add the same narrow source guard to both pinned copies: return no email
unless the validated JWT's top-level email_verified claim is the literal
boolean true. This blocks unverified email fallback, email backfill and email
association while preserving subject-ID lookup and verified email fallback.
Missing, false, strings and integer truthy values are not accepted. Tokens
whose providers omit email_verified can still use their configured subject
identity; they lose email-based linking. Normalized internal email claims also
require verification. No token claim is trusted before normal JWT validation.

The patch scripts are identical because each image has an isolated Docker
build context. Update both copies together. Apply only to the reviewed pinned
method shape; test its actual installed source before copying and again in
the final runtime. The standard-library checks execute the installed email
and user-info method bodies plus the actual fuzzy-lookup method against a
fake user table, without optional provider/database imports.
They cover unsafe claim values, normalized/nested email fields, verified
email fallback and subject-only identity. Negative controls with the guard
removed failed for both pinned upstream sources. Unverified claims caused
zero email lookups and zero identity-binding writes; verified linking worked. These are method boundary
tests, not an end-to-end IdP/database integration test.

Standalone LiteLLM retains 1.94.3 and increments its revision floor to 2.
Headroom remains 0.40.0; its existing candidate revision floor 3 includes
both this guard and the prior zlib patch. Existing package metadata remains
truthful. Xray may still report the upstream version; clearance requires a
fresh scan of the exact candidate digest.

Enable the existing LiteLLM workflow for matching pull requests so this
sibling fix receives candidate build/health/scan checks without publication.
Main publication remains manual; scan policy and service features stay intact.
